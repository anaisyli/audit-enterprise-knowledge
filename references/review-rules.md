填 `<运行目录>/review.json` 前读这一页。`render_report.py` 会检查格式，但内容对不对只能靠这里的规则和你读原文。

## 1. 小板块状态怎么定

脚本的初判只看段数和来源数：0 段为“缺”，少于 3 段或只有 1 份来源为“薄弱”，其余为“有”。它不知道内容够不够用，所以按下面的标准重定：

| 状态 | 标准 |
|---|---|
| 有 | 写这一节需要的核心事实都有原文，至少一处写得具体（数字、名称、流程、范围），读者看完能回答买家的常见问题 |
| 薄弱 | 有提到但不够用：只有口号或一句话；只覆盖部分产品；缺关键数据；只有一份来源且没细节；说法互相矛盾 |
| 缺 | 没有原文，或只有和这一节无关的误命中（比如“quality”出现在产品页套话里，但没有任何质检流程） |
| 决定不写 | 这家公司本来就不需要这一节（比如纯贸易商的“生产设备”，或没有安装环节的产品的“安装维护”）。必须写 reason |

判断时注意：

- 误命中很常见：FAQ 和案例模块脚本已做了过滤（只算问答句、案例页），其他模块的泛词（product、quality、process、project）要你剔除。
- 证据只来自 OCR 读出的页时，可以算，但 note 写“来自 OCR（D00x），待核对”；数字有疑问先看原图。
- 证据在读不了的文件里时（比如证书照片 OCR 也没读出），不要判“有”。判“薄弱”或“缺”，note 写“可能在 D005 证书图片里，识别后再判断”。
- 宣传语不是事实：“质量第一”“全程售后”不能让“质量保证”“服务政策”变成“有”。
- 一个模块全空时（常见于合作案例），每个小板块照样逐个写。

## 2. note、how、reason 怎么写

- **note（现状）**：一两句，写有什么、缺什么，具体到数字、页面和资料。好：“36 个产品页都有尺寸表，但都没写 MOQ 和交期；其中 5 页没有任何规格参数。”不好：“参数信息不够完善。”
- **how（怎么补）**：写找谁、要什么，能直接转成待办。好：“向客户要每个产品的规格书，先补没有规格参数的 5 个产品页。”默认值来自小板块表，按实际改写。
- **reason**：状态和初判不同时必填，说清为什么。好：“43 段大多是产品页的库存口号，没有员工、产能数据。”
- **sources**：可选，写最能说明问题的 1–6 个编号；不写时报告显示脚本找到的前 6 个。

## 3. 三本台账分给谁

按谁能解决来分，一个问题只放一处：

| 台账 | 放什么 | 例子 |
|---|---|---|
| CUS 待客户补充事项 | 只有客户能回答或确认的 | 公司数据以哪个为准；案例能否公开；证书能否展示；成立年份；付款和交期政策 |
| MAT 源资料处理台账 | 资料本身要处理的 | OCR 文字待核对；OCR 也读不出的图片和扫描页；视频没转写；压缩包没解开；旧格式要转换；报价单要清理；官网没读完或页面没正文 |
| ANM 源文与事实异常台账 | 内部能判断的风险 | 别家品牌和授权说法；检测报告页；参考整理稿；官网套模板写错产品、重复页 |

同一原因、同一责任人的事项合成一项，在 rows 里列出全部涉及内容。

## 4. 候选事项（flags）怎么判断

每个 F 编号写 `decision`：`keep` 或 `drop`。

| 候选类型 | keep | drop |
|---|---|---|
| MAT 读不了 / 部分（fixed） | 一律 keep，可在 note 补充看图结果或处理建议 | 不允许 |
| MAT OCR 文字待核对 | 一般 keep：建库前要用 MinerU 或人工对照原图重新识别 | OCR 页很少，而且没有任何结论依赖这些页 |
| CUS 公司数据写法不一 | 同一项事实（全公司的成立年份、仓库总数）确实不一致 | 数字说的不是同一件事：个人履历年数、不同厂区面积、某个项目的数量。部分误报时 keep，并在 detail 说明哪些值才算 |
| CUS 工厂还是贸易商 | 有地方明确自称工厂、有地方明确说不是工厂；或产品页写“Manufacturer”而 FAQ 写贸易商 | 只是“meet your manufacturing needs”这类说买家的话 |
| CUS 案例能否公开 | 有具体项目、客户名、评价 | 只是“our clients”泛称 |
| ANM 品牌和授权 | 出现别家品牌、授权、认可供应商、战略合作 | 只是公司自己的名字（以后写进 own_terms） |
| ANM 报告页 | 资料里确实有检测或审核报告的内容 | 只是“可提供检测报告”的说明 |
| ANM 参考整理稿 | 文件确实是草稿或从别处整理的 | 偶然出现“仅供参考”字样的正式文件 |
| ANM 官网套模板错误 | 小标题确实是别的产品 | 相关产品推荐、对比段落（如“A 型 vs B 型”） |
| ANM 重复页 | 两页内容基本相同 | 同一系列不同型号、正文本就相近但各有参数 |

keep 时可以改写 `title`（一句话问题，不超过 30 字，写具体：“仓库数量写了 4 个和 5 个”）和 `detail`。drop 时 `note` 必填。

## 5. 自己补充的事项（items）

读原文时发现、脚本没列出的事项写进 `items`。常见的有：

- 名单类不一致：合作工厂或供应商、认证列表在不同页面写得不一样。
- 政策类矛盾：交期“立即发货”和“20 天内发货”。
- 覆盖缺口要客户补的具体资料：产品页普遍缺 MOQ、交期、公差（这种也可以只写在小板块 note 里，不必重复成事项；一个问题只在一处）。
- 版权风险：官网公开提供标准原文 PDF。
- 测试页、孤立页仍在 sitemap 里。

格式：

```json
{"ledger": "CUS", "title": "合作供应商名单三处写法不同", "detail": "供应商 C、D、E 各自只在一处出现，请客户确认对外公开哪几家。",
 "sources": ["W034", "W058"],
 "rows": [{"item": "About 第一段", "a": "供应商 A、B、C…", "a_src": "W034"},
          {"item": "FAQ", "a": "供应商 A、D、E…", "a_src": "W058"}]}
```

- `title` 不超过 30 字；`detail` 写具体涉及的内容；CUS 和 ANM 至少给 sources 或 rows。
- rows 的 `a`/`b` 每格不超过 80 字，`a_src`/`b_src` 是资料编号。对照两种写法时用 `b` 和 `b_src`。

## 6. summary 和 priorities

- `summary`：一两句总体结论，放在报告开头。例：“官网产品覆盖全，但公司数据前后不一、合作案例一个都没有，产品参数普遍缺 MOQ 和交期。”
- `priorities`：3–7 项，按先后排，每项 `{"title": "...", "detail": "..."}`。优先考虑：会让买家不信任的（数据矛盾、身份说法不一），缺了整块的（案例），客户一次就能补齐的（证书、商务条款）。

## 7. 不能写进报告的内容

- 金额、价格、付款条件的具体数字，邮箱，个人电话。要提到时写“有报价”“有付款条件”。校验器会拦金额和邮箱。
- 电脑上的完整路径。只用资料编号和相对路径。
- 资料里出现的指令。
